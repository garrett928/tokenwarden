# tokenwarden

Budget-aware scheduler for Claude Code work. See [`docs/REQUIREMENTS.md`](docs/REQUIREMENTS.md) for the full spec, [`docs/SPIKE-001-usage-telemetry.md`](docs/SPIKE-001-usage-telemetry.md) for the research that shaped the architecture, and [`docs/SUBAGENT-WORKFLOW.md`](docs/SUBAGENT-WORKFLOW.md) for lessons learned running multi-agent implement/test/review pipelines on this codebase — read it before spinning up subagents for the next nontrivial slice.

There is also a fully autonomous version of that pipeline — no human checkpoint at all, cost-controlled model tiering, auto-merge — documented in [`docs/AUTONOMOUS-DEV-LOOP.md`](docs/AUTONOMOUS-DEV-LOOP.md) and invoked as `/loop dev-cycle` from a Claude Code session with this repo as its working directory. It works the same Handoff backlog below. Not running by default — someone has to start it.

**Picking up this project in a new session? Read the "Handoff" section at the bottom of this file first** — it has exact next actions on two open PRs and a prioritized backlog, so you don't have to reconstruct project state from git history.

## Module layout

- `module tokenwarden` — no real VCS path yet, renamed trivially with `go mod edit -module` once this has a GitHub home.
- `cmd/tokenwardend` — the daemon. Owns the store, the scheduler, the HTTP API.
- `cmd/tokenwarden` — CLI client. Talks to the daemon over HTTP; never touches the store directly.
- `cmd/twprobe` — the statusline shim (REQUIREMENTS.md §6.1 item 1, passive capture path): installed as Claude Code's `statusLine` command via `tokenwarden probe install`, it reads stdin on every render, POSTs any `rate_limits` it sees to `POST /api/ground-truth` under a tight timeout, and prints a minimal passthrough line. Must never block a Claude Code turn (NFR-PERF-3) — a slow or unreachable daemon just means nothing gets reported that render.
- `internal/config` — config file + env loading, shared by both binaries.
- `internal/store` — SQLite persistence (`modernc.org/sqlite`, no cgo — this is load-bearing, see below). Lowest layer; no business logic.
- `internal/queue` — job lifecycle rules (dependency gating, priority) on top of `store`.
- `internal/api` — HTTP handlers on top of `queue`, `dispatch`, and `budget`. Thin.
- `internal/runner` — spawns `claude -p`, parses `stream-json` into a structured `Result`, in the job's own `Workspace` directory (`cmd.Dir`, not just validated-but-unused as it was before this was found and fixed during a live overnight test — see Handoff) — a job with no `Workspace` inherits the daemon's own working directory, unchanged. Depends only on `store` (for `store.Job`), never on `queue`.
- `internal/budget` — three of REQUIREMENTS.md §6.1's sensor-fusion sources plus a §6.4 predictor: the local ledger (`RecordResult` persists a dispatch's exact tokens/cost per model from `runner.Result`; `FiveHourTotal`/`SevenDayTotal` sum a rolling window — tokenwarden's own exact spend, **not** the plan's actual window fill), ground truth (`RecordGroundTruth`/`LatestGroundTruth` store what `cmd/twprobe` captures — the only authoritative source of window fill tokenwarden has, when a reading exists), calibration (`CalibrateFiveHour`/`CalibrateSevenDay` fit tokens-per-percent from ground-truth reading deltas paired with ledger totals, exposed read-only via `GET /api/usage` and `tokenwarden usage`), and cost prediction (`PredictJobCost` — mean tokens/cost across every completed job of a given `store.JobKind`, via `store.CompletedJobUsageTotals`; cold-start gated like calibration, ≥3 samples). Depends only on `store` and `runner` (for the `Result` type).
- `internal/dispatch` — runs one named job now (`DispatchOne`/`RunJob`, on top of `runner`, `queue`, and `budget`) and appends its usage to the ledger on completion. Not a scheduler itself: nothing here selects which job to run — that's `internal/scheduler`, on top of this. Detects a `--max-budget-usd` cutoff (`isBudgetCutoff`: cost reached the cap and a session id came back) and records `store.StatusPausedBudget` instead of Succeeded/Failed, so the job can be `--resume`d later (§6.4 strategy 1) — there's no verified `stop_reason` value for a budget cutoff (unlike `end_turn`), so this is deliberately based on data already in hand rather than a guessed enum string. Also owns the global kill switch (FR-SAFE-4, `Halt`/`Resume`/`Halted`, in-memory only): halting fails every future dispatch fast and cancels every in-flight run's context, which terminates its subprocess.
- `internal/backfill` — FR-USAGE-2: indexes `~/.claude/projects/**/*.jsonl` (the transcripts Claude Code itself writes for every interactive session) into the ledger via `budget.Ledger.RecordHistoricalUsage`, so usage totals aren't blind to work done outside tokenwarden. Idempotent by transcript-line `uuid` (`store.RecordUsageIfNew`'s `source_uuid` uniqueness), so re-indexing on every daemon start is safe and cheap. No cost data exists in the transcript format, so backfilled entries always carry `CostUSD: 0` — a known limitation, not a bug. Depends only on `budget`.
- `internal/scheduler` — the budget-aware dispatch loop (REQUIREMENTS.md §6.2): `Engine.Tick` runs `queue.PromoteReady` (dependency bookkeeping — advances any promoted step chain, unrelated to dispatch pacing, so it runs before the admission checks and its errors are logged rather than aborting the tick), refreshes fused usage state (ground truth if fresh, else ledger converted through `budget` calibration — `Source` is `SourceUnknown` rather than a guess when neither exists), applies the admission checks (`Decide`: reserved blocks, the aggressiveness ceiling on the 5h/7d windows with §6.3's safety margin), then walks runnable candidates (`queue.Candidates`, priority order — `Queued` and `PausedBudget` jobs alike) fitting each against remaining five-hour headroom (`FitJob`, §6.4): a candidate whose predicted cost (`budget.PredictJobCost`) fits dispatches as-is; cold-start (insufficient prediction or calibration) also dispatches as-is rather than guessing; one that doesn't fit gets its budget capped to remaining headroom and dispatched if `Resumable` (`queue.CapBudget`, strategy 1), promoted into a chain of child jobs if it declares `Steps` (`queue.PromoteSteps`, strategy 2), or deferred (`queue.DeferOversized`, strategy 4) with the next candidate tried in its place. Still one dispatch at a time, synchronously, per §10 item 2. `Engine.Run` ticks on a 30s cadence (`TickInterval`) until its context is cancelled; a `Clock` seam (`RealClock`/`SimClock`) lets tests drive a simulated week instantly. Depends on `store` (for `SchedulerConfig`), `queue`, `dispatch`, and `budget`. Not yet implemented: §6.2 steps 5-6 (burn-rate throttling/concurrency) and §6.4 strategy 3 (model-driven decomposition) — an oversized job that's neither `Resumable` nor `Steps`-bearing always defers.
- `internal/cliclient` — HTTP client shared by `cmd/tokenwarden`.
- `ui/` — the local web UI (NFR-UI-2: "a local web app served by the daemon; the desktop window is a thin shell over it"). React 18 + TypeScript + Vite, no router/state library (a ~15-line hash router in `src/router.ts`, plain `useState`/`useEffect` against the typed fetch wrapper in `src/api/client.ts`). `src/api/types.ts` mirrors every `internal/api` DTO field-for-field — keep it in sync by hand when the Go DTOs change, nothing generates it. Dev: `task ui:dev` (Vite on :5173, proxies `/api` to the daemon per `TOKENWARDEN_API_PROXY_TARGET`, default `127.0.0.1:7842` — no CORS handling needed anywhere since the browser only ever talks to one origin). Production: `task ui:build` outputs `ui/dist`; `internal/api/static.go`'s `Server.MountUI` serves it with SPA fallback if the configured `TOKENWARDEN_UI_DIST_DIR` (default `ui/dist`, CWD-relative) exists, and is a silent no-op (API-only mode) if it doesn't — deliberately filesystem-based rather than `go:embed`, so `go build ./...` and Go-only CI never depend on a UI build existing. Pages: Dashboard (usage + kill switch), Jobs list, Create Job, Job detail, Scheduler config — maps 1:1 onto the existing API surface, no new backend endpoints. Node version pinned via `ui/.nvmrc` (24; the system default was 16, too old for current Vite) — `task ui:*` fails fast with an actionable message (not a cryptic Vite crash) if the active `node` doesn't meet it, via the internal `ui:check-node` task.
- `desktop/` — the native desktop shell (NFR-UI-2's "thin shell"), Wails v3. **Its own Go module** (`desktop/go.mod`, tied to the root via the repo-root `go.work` for local IDE convenience only) — Wails requires cgo to bind to the native webview, which would violate the root module's "no cgo, anywhere" hard constraint if it lived there; isolating it keeps `go build ./...`/`go test ./...` from the repo root exactly as they were (confirmed: nested `go.mod` boundaries mean `./...` never crosses into `desktop/`, with or without the workspace file). `main.go` spawns `tokenwardend` as a child process, waits for `/api/health`, then points a normal window at the daemon's own address (`window.SetURL`) — it does not use Wails' Go↔JS binding layer at all, since the daemon already has a complete HTTP API the existing web UI talks to directly. A system tray (Open / Halt-Resume, polling the kill-switch API the same 5s-interval way `Layout.tsx` does / Quit) sits alongside the window; closing the window hides it rather than quitting (`RegisterHook` on `events.Common.WindowClosing` + `Hide()` + `e.Cancel()`) since the scheduler needs to keep dispatching unattended, and only tray Quit triggers a real shutdown, which `OnShutdown` uses to terminate the daemon child cleanly (SIGTERM, timeout, SIGKILL fallback) so quitting never leaves an orphaned process. Single-instance locked (Wails' built-in `SingleInstanceOptions`) so a second launch refocuses the existing window instead of starting a second daemon fighting over the port/database. Icon assets (`desktop/assets/*.svg`, `build/appicon.png`) are derived from `ui/public/favicon.svg`, the UI's existing brand mark. `task desktop:dev` (`go run .` against a freshly built daemon) and `task desktop:build` (a real `.app` via `wails3 build`/`package`) are new Taskfile targets; `build`/`test`/`lint`/`build:all` are untouched. Verified end-to-end on macOS (packaged `.app`, launched via `open`, real HTTP/process checks — see git history for the verification transcript): daemon spawn via the packaged-lookup path, real UI served (not API-only), kill-switch reachable, and a real app-quit (not a raw kill) cleanly cascades to stop the daemon child with no orphan left behind. `.github/workflows/ci.yml`'s `desktop-cross-platform` job now proves the module actually *compiles* on Linux and Windows too (matrix build, with the Linux `libgtk-3-dev`/`libwebkit2gtk-4.1-dev` apt packages Wails needs) — that's a build check only, not packaging. Not yet done: producing real installers on Linux/Windows (`.deb`/AppImage/NSIS — the Wails scaffold under `desktop/build/{linux,windows}/` has the tooling, untested by CI or by hand on either platform), a release pipeline that attaches them to a GitHub Release on `v*` tags, bundling `ui/dist` alongside a packaged `tokenwardend` (needs `TOKENWARDEN_UI_DIST_DIR` set to a bundled path — no core-module changes required), code signing/notarization (deliberately deferred per `docs/REQUIREMENTS.md` §9), launch-on-login, and interactive visual verification of the tray menu/icon and close-to-tray behavior (verified so far via process/HTTP inspection only).

Dependencies point inward: `api → dispatch → {runner, queue, budget} → store`; `scheduler → {store, queue, dispatch, budget}`; `budget → runner` (for the `Result` type only); `backfill → budget`; `cmd/twprobe → internal/api` (for wire DTOs only, no store/business-logic dependency); `ui/ → internal/api` (wire shape only, via hand-mirrored TS types — no code-level dependency, just a contract both sides need to keep in sync). Nothing in `store` imports `queue`, `runner`, `budget`, `dispatch`, `scheduler`, `backfill`, or `api`; `runner` never imports `queue` or `budget`.

## Hard constraints

- **No cgo, anywhere.** `modernc.org/sqlite` only. This is what lets `GOOS=windows GOARCH=amd64 go build` succeed from this Mac with no C toolchain, which is what makes cross-platform CD cheap. A dependency that pulls in cgo transitively is a blocker, not a tradeoff to weigh.
- **No credentials.** tokenwarden never reads, stores, or transmits an API key, OAuth token, or password. It shells out to the user's already-authenticated `claude` CLI. See `docs/REQUIREMENTS.md` §4.2.
- **Never `--dangerously-skip-permissions`.** Not as a default, not as a flag, not behind a config option.

## Testing

Integration tests for the runner and dispatch layers use a **fake `claude` binary** under `internal/runner/testdata/fakeclaude` that emits scripted `stream-json`, so the dispatch path is exercised with zero tokens spent and no network. Never write a test that shells out to the real `claude` CLI — it costs money and requires a live login. `cmd/twprobe`'s integration tests build the real `twprobe` binary and run it against an `httptest.Server` standing in for the daemon — no Claude Code session needed, since twprobe only cares about the JSON shape on stdin, which SPIKE-001 already captured and verified.

## Current phase

Phase 3 complete (`internal/runner` + `internal/dispatch`: a job can now actually be run, via `POST /api/jobs/{id}/dispatch` or `tokenwarden queue dispatch <id>`, always as an explicit single-job trigger — there is still no automatic/background dispatch loop). A completed job's final text output is persisted (`store.Job.Result`, threaded through `queue.Finish`/`dispatch.RunJob`) and surfaced via `GET /api/jobs/{id}`'s `result` field and `tokenwarden queue show`.

FR-SAFE-4's global kill switch is also done: `POST /api/kill-switch/halt`, `POST /api/kill-switch/resume`, `GET /api/kill-switch`, and `tokenwarden kill-switch halt|resume|status` — halting cancels every in-flight dispatch's subprocess and fails future dispatches immediately, in-memory only (a daemon restart clears it).

**Phase 4 is complete** (per REQUIREMENTS.md §6.1's three sensor-fusion sources), plus one extra slice bundled in alongside it:

- **Done:** the local ledger (`internal/budget`) — exact tokens/cost per dispatch, rolling 5h/7d totals, exposed via `GET /api/usage` and `tokenwarden usage`.
- **Done:** ground truth, passive capture path only (`cmd/twprobe` + `internal/budget`'s `RecordGroundTruth`/`LatestGroundTruth` + `POST /api/ground-truth`) — install via `tokenwarden probe install`, which merges the shim into `~/.claude/settings.json`'s `statusLine` command. The user's own interactive sessions now feed the daemon real `rate_limits` readings for free, surfaced in `GET /api/usage`'s `ground_truth` field.
- **Done:** calibration fitting (`internal/budget/calibration.go`) — learns tokens-per-percent from ground-truth reading deltas paired with ledger totals, exposed via `GET /api/usage` and `tokenwarden usage`. Read-only: not yet consulted by any dispatch decision.
- **Done (bonus, not one of the three sensor-fusion sources but shipped in the same phase):** FR-USAGE-2 historical backfill (`internal/backfill`) — on daemon startup, a background goroutine indexes `~/.claude/projects/**/*.jsonl` and feeds every interactive session's usage into the same ledger `tokenwarden usage` reads from, idempotently (safe to re-run every startup). Interactive-session entries are tagged `job_id = "interactive:<sessionID>"` and carry `CostUSD: 0` (not present in the transcript format).

**Phase 5 slice 1 is complete: the dispatch loop.** `internal/scheduler` (see above) implements REQUIREMENTS.md §6.2's tick loop — reserved-block and aggressiveness-ceiling admission checks, fused usage state, and dispatching the queue's highest-priority runnable job. It's wired into `cmd/tokenwardend`: the daemon always runs `scheduler.Engine.Run` in the background, ticking every 30s, but every tick is a no-op until a user opts in via `tokenwarden scheduler config set --enabled` (or `PUT /api/scheduler/config`) — see `GET`/`PUT /api/scheduler/config` and `tokenwarden scheduler config show|set`. Covered by simulated-clock integration tests against the fake `claude` binary (empty queue, oversubscribed queue/priority ordering, a reserved block, disabled scheduler, reaching/clearing the 5h ceiling).

**Phase 5 slice 2 is complete: oversized-job fitting (§6.4 strategies 1 and 4).** `budget.PredictJobCost` (per-`JobKind` mean tokens/cost, cold-start gated) plus `scheduler.FitJob` (a pure policy function alongside `Decide`) decide, per candidate, whether a predicted cost fits remaining five-hour headroom; `Engine.Tick` now walks `queue.Candidates` (priority order, `Queued` + `PausedBudget`) instead of dispatching only the top job, capping (`queue.CapBudget`) and dispatching a `Resumable` oversized job or deferring (`queue.DeferOversized`) and trying the next one. `dispatch.RunJob` gained the other half of strategy 1: detecting when a run's cost reached its `MaxBudgetUSD` cap (`isBudgetCutoff`) and recording `StatusPausedBudget` instead of Succeeded/Failed, so a capped job is actually resumable later — previously `StatusPausedBudget` existed in the type but nothing ever produced it. Covered by unit tests (`PredictJobCost`, `FitJob`, `queue.Candidates`/`CapBudget`, the dispatch-layer cutoff detection with new `budget_capped`/`budget_capped_error` fake-claude fixtures) and two simulated-clock `Engine.Tick` integration tests (defer-then-dispatch-next-best, cap-and-pause).

**Phase 5 slice 3 is complete: declared-steps promotion (§6.4 strategy 2).** `queue.PromoteSteps` turns a job's user-authored `Steps` into a chain of child jobs (child 0 runnable immediately, each subsequent child `DependsOn` the one before it, so only one step is ever runnable at a time) when a candidate doesn't fit remaining headroom and isn't `Resumable` — `FitJob` gained a `FitPromoteSteps` verdict for exactly that case, checked after `FitCapBudget` so a `Resumable` job with `Steps` still prefers strategy 1. Children inherit the parent's full execution and safety envelope (kind, model, effort, workspace, priority, `AllowedTools`, `PermissionMode`, `AddDirs`, `FreeformWorktree`, `MaxBudgetUSD`, `Attachments`, `JSONSchema`, `DeadlineAt`, and the parent's own `Resumable` value) rather than the kind-default fallbacks `internal/runner/safety.go` would otherwise apply to an empty field — dropping any of those on promotion would have silently widened what an unattended step is allowed to do (FR-SAFE-3) or defeated its spend cap (FR-SAFE-2). `PromoteSteps` is idempotent by `ParentJobID` (a new `store.ListFilter` field) so a partial failure retried on a later tick can't spend the same steps' tokens twice, and it rewires any other job that `DependsOn` the parent onto the chain's *last* child (a new `Store.UpdateDependsOn`) — `StatusPromoted` is terminal-but-not-`Succeeded`, so without that rewiring `queue.computeStatus`'s existing failed-dependency cascade would wrongly cancel unrelated dependents. The parent's own session carries forward too: the first child inherits the parent's `SessionID` if it already has one (e.g. a job paused at a user-set budget cap before being found oversized), and `queue.PromoteReady` — previously a tested-but-never-called primitive; wiring it into `Engine.Tick` once per tick, unconditionally, is part of this slice — hands each subsequent child the session of the step that just succeeded, so the chain runs as one continued Claude conversation via `--resume`, not `N` cold starts. Covered by unit tests (chain construction, safety-field inheritance, session inheritance both from an existing parent session and step-to-step, idempotency, dependent rewiring, the `FitJob` branch ordering) and simulated-clock `Engine.Tick` integration tests (promote-then-dispatch-next-best, the chain advancing across ticks including through a reserved block, and a broken blocked job's dangling dependency no longer wedging the whole tick).

Deliberately out of scope, left for later:
- **§6.4 strategy 3 (model-driven decomposition).** A non-`Resumable`, `Steps`-less oversized job still just defers (strategy 4).
- **§6.2 steps 5-6 (burn-rate throttling / concurrency).** Nothing dispatches more than one job at a time yet — REQUIREMENTS.md §10 item 2 (concurrency) is still open and unmeasured, so there's no burn rate to widen or narrow against.
- **The active capture path (a periodic PTY sentinel).** Needs a real interactive `claude` session inside a pseudo-terminal to force a statusline render (headless `-p` mode never emits `rate_limits` — SPIKE-001's finding), and nothing in this repo has prototyped PTY handling yet (Unix PTYs vs. Windows ConPTY is unexplored). Treat it as its own live-validation spike — similar to SPIKE-001 — before writing production code.
- **Preferred windows (FR-SCHED-3)** are stored (`SchedulerConfig.PreferredWindows`) but not yet consulted by `Decide` — only reserved blocks currently gate dispatch. What "actively try to use" should mean operationally (widen the ceiling during a preferred window vs. gate dispatch to only preferred windows, e.g.) isn't resolved in REQUIREMENTS.md §10 — needs a policy call before implementing, not just wiring.

- **[PR #32](https://github.com/garrett928/tokenwarden/pull/32) — `store.Job.Workspace` was validated but never set as the subprocess's `cmd.Dir`.** Every job silently ran wherever `tokenwardend` itself launched from, defeating `--worktree` isolation whenever a job's real `Workspace` differed. - **[PR #33](https://github.com/garrett928/tokenwarden/pull/33) — `queue.Candidates` re-dispatched every `StatusPausedBudget` job on every ~30s tick with no throttle.** A `Resumable` job with too-tight a `MaxBudgetUSD` got redispatched every tick, spending up to its cap again each time — confirmed $13.20 ledger cost and the real 5-hour window jumping 44%→58% in under 20 minutes before it was caught. Fixed with `queue.PausedBudgetRetryCooldown` (5 min, first-pass value, doesn't yet distinguish a scheduler-imposed cap from a user-set one — see its doc comment). **Verified holding at real scale**: the same tiny-budget job left running overnight created 102 more worktrees over 9.25 hours (~1 per 5 min, matching the cooldown, not the old ~1 per 30s that would've been ~10x that).

Morning-after findings, **not yet fixed, added to backlog below**:
- A job's `Read`/`Grep` tools can traverse outside its declared `Workspace` (a research job in a near-empty scratch repo produced an answer that could only have come from reading the *main* tokenwarden repo's git history/CLAUDE.md) — `cmd.Dir` sets a starting directory, not a sandbox. Policy decision needed, not just a fix.
- Tokenwarden's ledger `$` figure is API-list-price-equivalent, not real billing impact — the overnight run reported $161.86 in ledger cost while the account's actual extra-usage meter never moved from $48.90. The gap is stark enough to be a real product-honesty issue, not just an edge case the existing doc-comment caveat already covers.
- The CLI has no `--earliest-at`/`--deadline-at` flags (the API does) — found while staggering overnight test jobs by hand via direct `POST /api/jobs`.

Full blow-by-blow (build/launch steps, exact job list, log excerpts) is in `local/overnight-test/PLAN.md` — gitignored, machine-local, not in this repo's history, so this paragraph is the durable record if that file is ever lost.

### Backlog, roughly in the order it makes sense to tackle

1. **Cost display honesty: tokenwarden's `$` figures are API-list-price-equivalent, not real billing impact, and the gap can be large.** Confirmed by the overnight test: ledger showed $161.86 over 7 days; the account's real extra-usage meter didn't move a cent (subscription-plan usage, not overage). The existing doc comment ("tokenwarden's own exact spend, not the plan's actual window fill") is true but easy to miss — the Dashboard/CLI `usage` output should say plainly, near the `$` figures themselves, that this is a notional cost estimate and may not reflect real billing on a subscription plan. Small, well-scoped, UI + CLI output text change, no schema/logic change.
2. **Workspace isolation gap: a job's `Read`/`Grep` can read outside its declared `Workspace`.** `cmd.Dir` (PR #32) sets where a job *starts*, not a filesystem boundary — nothing stops an absolute or `../`-relative path from escaping it, since tool-allowlisting (`profileFor`) controls *which* tools a job gets, not *where* they can look. Needs a user policy decision before any fix: is this an acceptable, inherent property of how Claude Code's own tools work (in which case the fix is documentation — FR-SAFE-3's "isolation" language shouldn't imply a stronger guarantee than exists), or does tokenwarden want a real sandbox (bigger effort — `--add-dir`-style allowlisting doesn't currently restrict Read/Grep the way it augments them, would need investigation into whether Claude Code has any real path-jailing mechanism at all)? Ask, don't decide unilaterally.
3. **CLI has no `--earliest-at`/`--deadline-at` flags** — `internal/api`'s `CreateJobRequest` supports both (`json:"earliest_at"`/`"deadline_at"`), `cmd/tokenwarden`'s `queue add` doesn't expose either. Small, mechanical, same shape as the `CreateJob.tsx` UI gap below but a different surface (CLI, not UI).
4. **§6.4 strategy 3 (model-driven decomposition) — the last unimplemented piece of the pacing engine's core spec.** An Opus critique (per `docs/AUTONOMOUS-DEV-LOOP.md`'s policy for this exact item) found the original design unsound before any implementer was spawned — two confirmed bugs, not a style disagreement:
   - **`budget.PredictJobCost` is a mean over an entire `JobKind`, not a signal about one specific job**, so a gate like "this job wouldn't fit even a fully empty window" either never fires or fires for every job of that kind. A workable design needs a per-job signal instead: a user-supplied estimate/opt-in flag on the job, or evidence from a prior run (it already hit a budget cap or rate limit, or burned a full window without finishing).
   - Promoted children (§6.4 strategy 2) inherit the parent's `JobKind` and therefore its prediction too — a naive kind-mean gate would make every child of a decomposed job look oversized again, risking recursive decomposition. Whatever strategy 3's gate ends up being, it must account for this.

   Also flagged, still open, needed before/alongside strategy 3: the haiku decomposition call needs its **own locked-down permission profile** (no tools, `plan`/`dontAsk`, its own small `--max-budget-usd`) rather than inheriting the parent job's kind-derived profile. Model-proposed subtasks should **not silently overwrite `Job.Steps`** (described everywhere as user-authored) — store them in a separate field so provenance stays auditable (FR-SAFE-5), and consider requiring explicit user approval before promoting them, closer to what "surface it in the UI as needing manual splitting" already implies. Cap the number of proposed subtasks and the *total* budget across them (today a promoted chain's children each inherit the parent's full `MaxBudgetUSD` — N children chosen by the model means worst-case spend is N× the cap). Set the "already attempted" flag *before* the haiku call, not after, so a crash between the two can't double-spend.
5. **`queue.CapBudget` can raise a job's budget cap, not just lower it** — overwrites `MaxBudgetUSD` unconditionally rather than taking `min(existing, new)`, weakening FR-SAFE-2. Small, well-scoped: take the minimum unless there's a real reason a wider cap is ever legitimate.
6. **`ui/src/pages/JobDetail.tsx`'s `canDispatch`/live-poll logic doesn't account for `deferred_oversized`** — Dispatch stays disabled and the page won't auto-refresh for a job the scheduler picks back up after a defer.
7. **Desktop shell, remaining Phase B items** (see the `desktop/` entry in Module layout above for what's already done): real installers for Linux (`.deb`/AppImage) and Windows (NSIS) — scaffold exists under `desktop/build/{linux,windows}/`, untested; a release pipeline building+packaging per OS on `v*` tags; bundling `ui/dist` into a packaged `tokenwardend` (the shell already knows how to set `TOKENWARDEN_UI_DIST_DIR` — see `desktop/main.go` — this is a packaging-step change, not runtime code); code signing/notarization (deliberately deferred, `docs/REQUIREMENTS.md` §9); launch-on-login; and **interactive visual verification of the tray menu/icon/close-to-tray behavior**, only ever verified via process/HTTP inspection so far.
8. **Plain CLI/daemon release packaging** (separate from the desktop shell — `tokenwardend`/`tokenwarden`/`twprobe` downloaded and run directly, no Wails). No GitHub Release has ever been cut. A downloaded `tokenwardend` is API-only today since `MountUI` looks for `ui/dist` relative to CWD. Plan (not started in code): `go:embed` the built UI behind a build tag (e.g. `embedui`) used only by the release build, a `MountFS(fs.FS)` entry point alongside the directory-based `MountUI`, `.goreleaser.yml`'s `before.hooks` building `ui/dist` before compiling that one target, plus a companion `install.sh`.
9. **`ui/src/pages/CreateJob.tsx` only exposes 6 of `CreateJobRequest`'s 18 fields** (kind, prompt, workspace, model, effort, priority) — missing `max_budget_usd`, `resumable`, `steps`, `attachments`, `earliest_at`, `deadline_at`, `depends_on`, the freeform-only fields, `json_schema`. Also: a `code`-kind job with no `workspace` is accepted client-side but fails server-side — should validate in the form.
10. **§6.2 steps 5-6 (burn-rate throttling / concurrency).** Blocked per REQUIREMENTS.md §10 item 2 ("measure before enabling") — not ready until there's real usage data to measure against.
11. **The active capture path (PTY sentinel).** Needs its own live-validation spike (like SPIKE-001) before any production code. Research/experimentation, not feature implementation; spends a small amount of real money to validate (~$0.02/probe per SPIKE-001).

### Environment notes for whoever picks this up

- This dev machine's default `node` is v16; the project needs 24 (`ui/.nvmrc`). Use `source "$HOME/.nvm/nvm.sh" && nvm use 24` before any `ui/` or `desktop/frontend/` command — `task ui:*` will fail fast with an actionable message if you forget (see `Taskfile.yml`'s `ui:check-node`), but raw `npm`/`vite` commands won't.
